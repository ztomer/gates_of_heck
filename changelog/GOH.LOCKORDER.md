* ONE lock order (GOH.LOCKORDER): `lib/lock_order.tsv` ranks every lock goh takes (lander < ship < land < load < bench < gate_slot < tree < container < desktop < gpu < the leaf locks), and every acquisition goes through `lib/lock_order.py` / `lib/lock_order.sh`, which refuse a WAIT (exit 78, naming both locks and the table) on a lock ranked at or below one this process or an ancestor holds (`GOH_HELD_LOCKS`). goh v0.122.0's ship deadlocked on 2026-11-15: it held the land lock and its loaded suite waited 1800 s for the load slot, which a land held while queued on the land lock (`load.py 0 -- bash tools/land.sh`). `tools/land.sh` now takes the land lock FIRST and runs its gate in the load slot itself, so a queued land holds nothing; **run it bare, `bash tools/land.sh`** -- run inside the load slot it is refused at once (`tests/test_lock_order_deadlock.py`, red on the old order).
* `checks/check_lock_order.py`, a `GOH_CI_STEPS` step: no raw `fcntl.flock` (or unmarked Rust file lock) outside the helper, the table names exactly the files that take each lock, and the held-while-acquiring graph derived from the tree sorts topologically -- a cycle is red, named edge by edge, as is an edge against the ranks (`tests/test_check_lock_order.py` re-plants the 2026-11-15 order and watches it go red).
